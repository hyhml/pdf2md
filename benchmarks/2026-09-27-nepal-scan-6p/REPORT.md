# 《尼共毛（汪亭友）测试.pdf》PDF 转 Markdown 工具对比报告

## 结论

原来的整本强解析任务已经暂停，本次只测试 6 页文件 `尼共毛（汪亭友）测试.pdf`。四种工具均已得到可检查结果，源 PDF 未被修改。

对这份样本，结论如下：

1. **Marker 2 的成品质量最好**：目录条目和页码恢复最完整，正文、脚注、链接的 Markdown 表达也最好。但它在本机 CPU 上耗时 **761.80 秒（12 分 42 秒）**，默认后端还依赖 Docker；改用本地 llama.cpp 后才跑通。它适合作为疑难页的精解析器，不适合在当前 CPU 环境直接全书逐页跑。
2. **Docling 是综合折中最好的一项**：首次完整运行 43.35 秒，正文识别接近 Marker，脚注也没有被整体丢弃。主要问题是三页目录被输出成“单单元格大表格”，编辑性差；第 4 页脚注的内部顺序也有错位。
3. **PP-StructureV3 的正文较干净，但目录和脚注表现不理想**：正文段落、标题和页序基本正确；目录有漏字、漏页码；默认 Markdown 直接忽略脚注。峰值内存约 3.97 GiB，是本次最高。
4. **OCRmyPDF 最快、最省内存，但不是结构化 Markdown 工具**：8.30 秒即可产生带分页符的 OCR 旁文本和可搜索 PDF，适合建立搜索层；目录乱码和正文错字明显，输出没有标题、表格或脚注语义。

如果目的是处理整本书，建议采用组合方案：**OCRmyPDF 建搜索层 + Docling 批量生成正文草稿 + Marker 只复核目录、脚注和低质量页**。若只在这 6 页中选择一个最终底稿，则选 Marker 2，但需要人工修正第 4 页脚注顺序和个别繁简字。

## 测试对象与环境

- 输入文件：`尼共毛（汪亭友）测试.pdf`
- 页数：6 页
- SHA-256：`62aa011553c4e36999e14d7c50f6ba1e3578b7ce29c1cd3817a93b1e80c3b246`
- 内容构成：第 1–3 页为密集目录；第 4–6 页为正文，含标题、页眉页脚、长脚注和英文文献。
- 运行环境：WSL2，Intel Core i7-12700H，20 逻辑 CPU，7.6 GiB 内存，CPU-only。
- 四项测试均在本机完成，没有把 PDF 上传到云端服务。

“原始 Markdown”是工具直接产生、未经人工修订的结果；`*.paginated.md` 是为了统一检查页码而生成的派生副本，只增加 `<!-- PDF_PAGE: n -->` 和 `# PDF 第 n 页`，没有纠正 OCR 文字。

## 性能与部署对比

| 工具 | 版本/配置 | 完整结果 | 墙钟时间 | 最大 RSS | 部署与运行说明 |
|---|---|---:|---:|---:|---|
| OCRmyPDF | 16.13.0；Tesseract 4.1.1；`chi_sim+eng`；force OCR | 成功 | **8.30 秒** | **144,180 KiB**（约 141 MiB） | 本地补齐 Ghostscript 9.55.0；同时产生可搜索 PDF |
| Docling | 2.130.0；RapidOCR；full-page OCR；CPU | 成功 | **43.35 秒** | **2,378,532 KiB**（约 2.27 GiB） | 时间包含首次下载 18.36 秒版面模型；另一次为生成 JSON 的运行与 Marker 并发，未纳入横向计时 |
| PP-StructureV3 | PaddleOCR 3.5.0；PaddlePaddle 3.2.0；CPU | 成功 | **70.60 秒** | **4,160,112 KiB**（约 3.97 GiB） | 此数为模型已缓存后的完整运行；第一次冷启动在 206 秒时因缺少可选 `python-docx` 失败，补齐后复测成功 |
| Marker 2 | marker-pdf 2.0.0；Surya 0.22.1；fast + force OCR；llama.cpp CPU | 成功 | **761.80 秒** | **1,587,980 KiB**（约 1.51 GiB，命令报告口径） | 默认 vLLM 后端先运行 66.01 秒后因无 Docker 失败；改用 llama.cpp b11212 后成功，模型/缓存约 1.8 GiB |

这些时间是本机这一次实测，不是跨机器基准。按 6 页结果做纯线性估算，400 页大约为：OCRmyPDF 9 分钟、Docling 48 分钟、PP-StructureV3 78 分钟、Marker 2 14 小时。长文档批处理、缓存命中和页面复杂度都会改变实际时间，因此该估算只用于判断量级。

为避免污染系统 Python，本次给四个工具建立了独立虚拟环境，并把模型、Marker 的 llama.cpp 运行时和 OCRmyPDF 的本地 Ghostscript 一并保存在交付目录中；整个 `pdf-tool-comparison/` 当前约占 **8.4 GiB**。真正的 Markdown、JSON、图片和 PDF 产物远小于这个数字，大部分空间是可重建的依赖与模型缓存。

## 分项目分析

### Marker 2

优点：

- 第 1 页目录被正确输出为两列表格，标题、条目和页码基本完整。
- 第 2 页目录虽然没有全部转成表格，但条目和页码的恢复远好于其他工具。
- 正文段落连续，标题、上标脚注、斜体英文题名和 URL 都有较好的 Markdown 表达。
- `--paginate_output` 直接保留了 0 起始页标记；派生副本已映射为 PDF 第 1–6 页。

问题：

- 默认扫描页 OCR 后端选择 vLLM，需要 Docker；本机没有 Docker，所以默认路径不能直接运行。
- CPU 替代路径还需要单独安装 llama.cpp，并下载约 1.8 GiB 的 Surya GGUF/版面模型。
- 速度最慢，约 127 秒/页。
- 第 4 页的长脚注分成多个块后顺序错误：脚注后两段被排在脚注第一段之前。文字基本都在，但语义阅读顺序需要人工调整。
- 原文简体“觊觎”被输出为繁体“覬覦”。这不是语义错误，但不忠于原字形。

### Docling

优点：

- 首次运行即成功，速度明显快于 PP-StructureV3 和 Marker。
- 正文中“边陲”“垂涎”“清剿”等几个易错词均识别正确。
- 脚注和英文文献被保留，JSON 中还保留页级来源信息，可重新导出带分页标记的 Markdown。
- 页眉页脚没有大量混入正文。

问题：

- 三页目录被版面模型判断为表格，但每页几乎都压进一个巨大单元格；条目不再逐行可编辑。
- 目录中的若干页码缺失或与文字粘连。
- 第 4 页脚注虽然保留，但脚注行块的内部次序有错位。
- CLI 直接导出的原始 Markdown 没有页分隔符；本报告利用同次配置导出的 JSON，调用 Docling 自己的 Markdown 导出器加入分页标记。

### PP-StructureV3

优点：

- 每页单独生成 Markdown，天然能追溯到 PDF 页码。
- 第 4–6 页正文的段落合并、标题识别和阅读顺序总体较好。
- 同时生成 JSON、DOCX、TeX、版面框图和 OCR 可视化图，方便问题定位。

问题：

- 密集目录页存在较多漏字、错字和漏页码，例如“研究现状”被识别成“研现状”，“普拉昌达”有漏字。
- 默认 `markdown_ignore_labels` 包含 `footnote`、`header` 和 `number`，所以第 4、6 页脚注以及页码没有进入 Markdown。对要求内容完整的书籍，这是实质性缺失。
- “边陲”被识别为“边睡”，“觊觎”被识别为“凯觎”。
- 内存峰值约 3.97 GiB；第一次模型初始化和依赖补齐也较重。

### OCRmyPDF

优点：

- 速度最快、内存最低。
- 原始旁文本使用换页符分隔 6 页，页码映射可靠。
- 额外生成体积约 682 KiB 的可搜索 PDF，可用于全文检索或给其他工具提供文字层。

问题：

- 它的旁文本只是纯文本，扩展名虽为 `.md`，实际没有 Markdown 标题层级、表格和脚注语义。
- 目录点线、细小字体和中英文混排导致明显乱码。
- 正文错字比另外三项多，例如“边陲→边隆”“垂涎→垂洗”，还有成段中文被误成拉丁字符。
- 适合作为检索基线，不适合作为可直接编辑或出版的 Markdown 原稿。

## 最终建议

- **追求这 6 页的最高可用质量**：以 Marker 2 结果为底稿，人工修正第 4 页脚注顺序和“覬覦”的繁简字。
- **追求整本书的实际吞吐量**：以 Docling 批量转换；目录页、复杂脚注页再送 Marker；用 OCRmyPDF 产出的可搜索 PDF 做检索和交叉核对。
- **PP-StructureV3 若继续使用**：必须调整脚注忽略配置，否则会在看似干净的 Markdown 中静默丢失脚注；同时需要为其预留约 4 GiB 峰值内存。
- **OCRmyPDF 不应单独承担最终 Markdown 交付**：它适合做底层 OCR/搜索层，而不是结构化正文。

本次只做了 6 页人工目检和 12 条机械抽样，没有宣称完成逐字校勘。原整本强解析任务保持暂停状态。
